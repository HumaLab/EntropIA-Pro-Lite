# Agent corpus tools — stage 3 of PLAN-AGENTES-ENTROPIA.md, corpus half

Lets a paired assistant read documents by pages and passages with citable locations, edit the corpus
(collections, item metadata, recognized text), import files and delete with protection, through the
loopback MCP endpoint. Builds on `odd/tasks/agent-processing-tools.md` (PR #207, merged at 32ebcc16).

## Decisions

- D1 — Delivery in slices, all accumulated before one version (L1): A read (T1-T2), B edits (T3-T4),
  C import (T5), D delete (T6), E per-document media operations (T7). Each slice: TDD, full Rust and desktop
  suites, `pnpm format:check`, docs, one independent verify at the slice end when it touches a high-risk item.
  Slices are commits on `feat/agent-corpus-tools`; pushing and opening PRs is the owner's call (L4).
- D2 — Text is located, not identified (exploration L2): extraction and chunk rows get new random ids on every
  re-extraction, so a citation is `itemId` + `assetId` + `pageNumber` + `startChar`/`endChar` + `textHash`
  (sha256 of the page text the offsets index). A changed hash tells the assistant its citation is stale.
- D3 — Page text follows the app's own rule (`lib/page-text.ts` `readPageSource`): the latest extraction when
  non-empty, otherwise the latest transcription. Reads are windows (default 4000, max 20000 characters) with an
  opaque cursor, never the whole document by default.
- D4 — Passage search uses the existing `rag_chunks_fts` index (chunks exist only for embedded documents); the
  result says how many items in scope have no passages yet, instead of implying full coverage.
- D5 — Confirmation (S5): deleting anything, importing from the file system and overwriting recognized text go
  through the owner's approval in the app (the approvals of PR #207, new actions). Creating or renaming a
  collection and editing item title/metadata are `local_write` without a dialog, revision-fenced by
  `updatedAt` and audited. Owner may tighten this later.
- D6 — Mutations move to Rust services and the UI callers move to them (S6); no tool reuses `db_execute`.
- D8 — UI migration seam (S6): the app's store is built once in `initDb()` (`lib/db.ts`); there
  `collections.create/update` and `items.update` are routed to the Rust commands (`lib/corpus.ts`), so every view
  and dialog takes the new path without changing, and their tests (which mock the store) stay as they are. The
  app path sends the item metadata as the JSON it already builds (reserved keys included, as import writes them);
  the agent path sends plain fields and the service keeps the reserved keys and refuses to write them. Both share
  validation, revision fencing and the search refresh.
- D9 — Import sources (owner, L10): an assistant may only propose files inside folders the owner enables in
  Settings › Asistentes ("carpetas de entrada"). Paths are resolved (symlinks included) and must stay inside an
  enabled folder; every import still needs the owner's approval, with the list of files shown.
- D7 — No migration (sync `schema_tag`): every write goes through the tables' existing sync triggers, which fire
  on any connection.

- D10 — T5b design (parent, 2026-11-02, from reading `collection-import.ts`): (a) one Rust command for the app, `corpus_import_path(collectionId, sourcePath, overrides)`, built on `corpus::ingest::import_file`; the owner chose the path (picker, drop, Internet Archive or Navegador staging, sample collection), so it skips the enabled-folder rule but keeps `missing`, `not_a_file`, `unsupported` and `too_large`; `in_archive` stays unless a caller stages inside the data dir, in which case only `<data_dir>/assets` is refused. (b) `import_file` takes the app's overrides: `title`, stored `fileName`, `extraMetadata` (added beside `__entropia_file_metadata`, never replacing it) and `allowDuplicate`; the agent passes none. (c) `importedAt` gets millisecond precision, as the app writes it. (d) `importClassifiedPathsIntoCollection` keeps its signature, result and progress stages, and calls the command once per classified file; its in-process claim map stays, so a concurrent import of the same path still waits and imports itself when the other failed. (e) The renderer's copy, PDF split, dedupe and discard paths are removed when nothing else uses them; fs-plugin grants stay unless no caller is left.

- D11 — T6 delete (owner, L16; design by the parent from the exploration in L16): (a) one Rust service, `corpus::delete`, reproduces the app's cascades (`item.repo.ts` `deleteWithCascade`, `collection.repo.ts` delete) in one `BEGIN IMMEDIATE`: every table the repos delete explicitly, `fts_items` by rowid, `vec_assets` when the table exists, the FTS vocabulary forgotten as the repo does; sync triggers record the `D` tombstones as for any app write. (b) Database first, files after the commit: the item folders `assets/<collection>/<item>` and the thumbnails; a file that cannot be removed is logged and left to the startup orphan sweep, never undeleting rows. (c) `delete_impact` counts what is lost (documents, pages, notes, annotations, documents with recognized text) for the dialog and the assistant. (d) The app's item and collection deletes move to two commands on that service; page (asset) deletion stays in the renderer for now. (e) Assistants: `documents_delete` (1-200 item ids) and `collections_delete` (collection id), `local_write`, always an owner approval showing the impact, «No se puede deshacer y se borra en todos tus equipos», focus on «Rechazar»; the approval is bound to the exact set (ids plus each item's `updatedAt` and asset count, hashed), so a document that changed or a collection that gained or lost one before the answer fails the approval and nothing is deleted.
